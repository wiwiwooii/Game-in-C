# Создание архитектуры приложения и бэкенда

Командой разработки была создана и описана архитектура бэкенда приложения. Это важный этап, потому что он определяет, как будет устроена техническая часть продукта и как разные части приложения будут взаимодействовать между собой.

## Архитектура приложения

~~~text
backend/
│
├── cmd/
│   └── main.go              # Точка входа
│
├── internal/
│   ├── handler/             # HTTP-обработчики, контроллеры
│   ├── service/             # Бизнес-логика
│   ├── repository/          # Работа с базой данных
│   └── model/               # Структуры данных
│
├── pkg/                     # Общие утилиты: логгер, конфиг
│
├── config/                  # Конфигурация окружения
│
├── migrations/              # SQL-миграции
│
└── go.mod
~~~

## Пример структуры API

~~~text
Курсы и уроки

GET    /api/v1/courses                  — список курсов, фильтр: method, level
GET    /api/v1/courses/:id              — детали курса
GET    /api/v1/courses/:id/lessons      — список уроков курса
GET    /api/v1/lessons/:id              — детали урока с упражнениями
~~~

## Замечания от группы тестирования

Также группой тестирования были внесены замечания, которые важно рассмотреть заранее, чтобы в будущем избежать проблем при развитии приложения.

Одно из замечаний касалось модели `user_progress`.

> Слишком упрощённая модель `user_progress`. Сейчас мы фиксируем только базовые данные о прохождении уроков, и этого недостаточно для дальнейшего развития системы. Из-за этого мы ограничены в возможностях анализа поведения пользователя. Например, мы не можем глубоко отслеживать ошибки, динамику обучения или слабые места пользователя. Если расширить аналитическую модель, это откроет возможность для более продвинутых функций: адаптивного обучения, системы анализа ошибок, а также персонализированных рекомендаций под каждого пользователя.

После разбора замечаний группа разработки учла предложения тестирования и внесла необходимые корректировки в дальнейшее планирование архитектуры.
